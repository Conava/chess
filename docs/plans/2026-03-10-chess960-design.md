# Chess960 (Fischer Random Chess) — Design Document

Date: 2026-03-10
Status: accepted

---

## Overview

This document specifies how Chess960 (Fischer Random Chess) will be added to the engine as a
new `Ruleset` implementation. The goal is a full, correct Chess960 experience that reuses as
much existing logic as possible while touching no more than the minimum set of files needed.

Chess960 differs from standard chess in exactly two ways:
1. The back-rank starting position is randomized (960 valid positions exist).
2. Castling must find the rook dynamically — it cannot assume a1/h1/a8/h8.

Everything else — pawn rules, en passant, promotion, check/checkmate/stalemate, 50-move rule,
threefold repetition, insufficient material — is identical to `StandardChessRuleset`.

Scope covers **offline play** and **online server play**. The server decides the starting
position and communicates it to both clients via the existing message protocol.

---

## Key Decisions

### Decision 1: Position Generation — on-the-fly constrained random

**Chosen:** On-the-fly constrained random generation, not a lookup table.

The constrained-random algorithm is simple, easy to test, and produces every one of the 960
valid positions with uniform probability:

1. Place a bishop on a random dark square (files 0, 2, 4, 6).
2. Place a bishop on a random light square (files 1, 3, 5, 7).
3. Place the queen on a random remaining square.
4. Place the two knights on two random remaining squares.
5. The three remaining squares receive, left-to-right: Rook, King, Rook.
   (This guarantees king-between-rooks by construction — no validation pass needed.)

The position is stored as the actual back-rank `Pieces[]` array on the ruleset object. It is
also derivable as a Scharnagl index (0–959) but that computation is deferred — the index is
not needed by any feature in this scope.

### Decision 2: Code Reuse — abstract base class

**Chosen:** Extract `AbstractChessRuleset` as a shared base; both `StandardChessRuleset` and
`Chess960Ruleset` extend it.

Composition (Chess960 delegates to Standard) was considered but rejected: the shared methods
are not a collaborator relationship, they are shared behaviour. Direct delegation via wrapping
would require exposing `getSudoLegalSquares` as package-visible or public, which leaks
internals. Copy-with-modifications was rejected outright — any bug fixed in one copy would
silently stay in the other.

The abstract base class owns:
- `getLegalMoves` (the `Square`→`Move` projection)
- `getLegalSquares` (the deep-copy check filter, including the transit-square castling check)
- `getSudoLegalSquares` dispatch (rook, knight, bishop, queen, pawn)
- `isCheck` and `canBeCaptured`
- `isValidSquare`, `isInBoundsX`, `isInBoundsY`
- `getWidth` / `getHeight` (default 8)

`StandardChessRuleset` becomes a one-method subclass: just overrides `getStartBoard`.

`Chess960Ruleset` overrides `getStartBoard` and `getPseudoLegalKingSquares` (the method that
decides castling candidates — see Decision 3 below).

### Decision 3: Castling in Chess960

**Root problem:** `PossibleStandardKingMoves` encodes castling destination squares as hardcoded
`x=2` (queenside) and `rowCount-2` (kingside). `Board.handleCastleMove` encodes rook origin
as `x=0` and `x=7`. Both of these are wrong for Chess960.

**Chosen approach: king-moves-to-rook-file encoding**

The most robust Chess960 approach is to encode the castling intent as "king moves to the
rook's file" rather than "king moves 2 squares". This is the FIDE-sanctioned disambiguation
convention for Chess960 notation.

**`PossibleChess960KingMoves`** (new class):
- `canCastleToward` walks the board dynamically to find an unmoved friendly rook. The
  destination square added to the pseudo-legal list is the **rook's actual file** (not x=2
  or x=6). This makes the castling intent unambiguous.

**`CastleMove`** (modified):
- Adds `rookOriginFile` (default -1) and `kingDestFile` (default -1) fields.
- Adds a second constructor: `CastleMove(Square start, Square end, int rookOriginFile, int kingDestFile)`.
- Existing zero-extra-fields usages are unchanged.

**`Board.handleCastleMove`** (modified):
- If `rookOriginFile >= 0`: use explicit values — rook comes from `rookOriginFile`, king
  lands on x=2 (queenside) or x=6 (kingside), rook lands on x=3 or x=5.
  Queenside/kingside determination: `kingDestFile < kingStartFile` = queenside.
- Otherwise: existing hardcoded logic unchanged.

**`Game.movePiece`** (modified):
- Standard castling detection: `king moves exactly 2 squares horizontally`.
- Chess960 castling detection (additional): `king moves to a square occupied by an unmoved
  friendly rook`. This second condition never fires in a standard game (rooks start on a/h
  files and the king never moves there via normal play).
- When either condition fires, creates `CastleMove(start, end, rookOriginFile, kingDestFile)`.

**`Chess960Ruleset.getLegalSquares`** (overrides the castling transit check):
- Detection condition changes from `Math.abs(delta)==2` to `destinationSquare.getPiece() instanceof Rook && destinationSquare.getPiece().getPlayer().equals(movingPlayer)`.
- Transit-square check walks all squares between the king's current position and its actual
  landing file (c or g), not just one step.

### Decision 4: Wire protocol — Scharnagl index

**Chosen:** Send the Scharnagl index (0–959) as a single integer in the `CREATE_GAME` message.

**Analysis of the two options:**

Option A (Scharnagl index): compact, one integer, both sides reconstruct the position
deterministically. Requires `Chess960StartPosition` to compute the index from the generated
layout (a pure math operation on the back rank). The index is also the natural format for
display (e.g. "Position 518 = standard").

Option B (piece-type array): avoids index computation, but requires serializing 8 strings
(`"RBNQKBNR"`) and parsing them on the client. More bytes, more parsing surface, no benefit.

**Chosen: Scharnagl index.** One extra integer in the existing key=value content format.

**Wire changes:**

`CREATE_GAME` message for Chess960 adds one key:
```
ruleset=CHESS960 playerName=<name> position=<index>
```

The `position` key is absent for `ruleset=STANDARD` (clients ignore absent keys).

`GameInstance.startGame()` passes the index to `Game.createServerGame()` via a new optional
`Map<String, String>` parameter (consistent with how `createGame()` already accepts
`onlineGameSettings`). The server generates the position using `Chess960StartPosition`, stores
the Scharnagl index, and includes it in the `CREATE_GAME` message forwarded to the joiner.

**How `Chess960Ruleset` accepts an external position:**

Two constructors:
- `Chess960Ruleset()` — generates a random position internally. Used for offline play.
- `Chess960Ruleset(int scharnaglIndex)` — reconstructs the back rank from the given index.
  Used by the server game and by the joining client who receives the index from the server.

The Scharnagl reconstruction algorithm (index 0–959 → back rank) is a standard deterministic
formula. It is implemented in `Chess960StartPosition` alongside the random generator, so both
live in one place.

**Client flow for online Chess960:**

1. Creator sends `CREATE_GAME ruleset=CHESS960 playerName=...`. Server generates a random
   Chess960 position, stores the index, sends `JOIN_CODE joinCode=<id>` back. This `JOIN_CODE`
   message is extended to also carry `position=<index>` when the ruleset is Chess960.
2. Creator receives `JOIN_CODE position=<index>` and constructs `Chess960Ruleset(index)`.
3. Joiner sends `JOIN_GAME gameId=<id> playerName=...`. Server sends back a `SUCCESS` message
   extended with `position=<index> ruleset=CHESS960`.
4. Joiner constructs `Chess960Ruleset(index)` from those parameters.
5. Both clients are now in the same Chess960 position.

The `JOIN_CODE` and `SUCCESS` messages are currently key=value strings — adding `position` and
`ruleset` keys is a backward-compatible extension.

**Server changes required:**
- `Chess960StartPosition` exposes `getIndex()` returning the Scharnagl index.
- `GameInstance` stores the index when ruleset is Chess960 and injects it into the
  `JOIN_CODE` and `SUCCESS` messages.
- `Game.createServerGame` gains an overload or `Map<String, String>` parameter to accept the
  index, allowing `GameInstance` to tell the game layer which position to use.

### Decision 5: `RulesetOptions` pretty names

**Chosen:** Add a `displayName` field to `RulesetOptions`, override `toString()` to return it,
and use the existing `ComboBox<RulesetOptions>` rendering unchanged (it already calls
`toString()`).

```java
public enum RulesetOptions {
    STANDARD("Standard Chess"),
    CHESS960("Chess 960");

    private final String displayName;
    RulesetOptions(String displayName) { this.displayName = displayName; }

    @Override
    public String toString() { return displayName; }
}
```

The `ComboBox` in both `offline-setup.fxml` and `online-setup.fxml` calls `toString()` on each
item. No FXML or controller change is required — updating the enum is sufficient.

The server uses `RulesetOptions.valueOf(message.getParameterValue("ruleset"))` to parse
incoming values. `valueOf` uses the enum constant name (`STANDARD`, `CHESS960`), not
`toString()`, so the server parse is unaffected by the display name change.

### Decision 6: Position ID / Reproducibility

The Scharnagl index is computed by `Chess960StartPosition` at generation time and exposed via
`getIndex()`. `Chess960Ruleset` stores it. No position label is shown in the UI (as confirmed
by the user), so `GameController` does not need to read it.

### Decision 7: Match setup UI redesign

**Scope:** `offline-setup.fxml`, `online-setup.fxml`, and their controllers
(`OfflineSetupController`, `OnlineSetupController`).

**Current state:** Both dialogs are minimal `VBox` layouts — a title, flat label+field pairs
stacked vertically, and a footer button row. They use `overlay-card` (already styled), the
existing form-control CSS classes, and i18n keys. The structure is functionally correct but
lacks visual grouping and hierarchy.

**Proposed redesign:**

The CSS foundation is already good: `overlay-card`, `dialog-title`, `text-field`, `combo-box`,
`btn-primary`, `btn-ghost`, `section-heading`, `card`, and themed token variables
(`app-primary`, `app-surface`, `app-border`, etc.) are all in place. The redesign uses only
these existing classes — no new CSS needed.

**Offline setup (`offline-setup.fxml`) redesign:**

```
overlay-card (VBox, spacing=20, minWidth=420)
├── Label "Game Setup"                     [dialog-title]
├── GridPane (2 cols: Label col 35%, Field col 65%, vgap=10 hgap=12)
│   ├── Label "White Player"  | TextField fx:id="whiteField"
│   └── Label "Black Player"  | TextField fx:id="blackField"
├── Separator
├── Label "Rules"                          [section-heading]
├── ComboBox fx:id="rulesetBox" maxWidth=Infinity
└── HBox alignment=CENTER_RIGHT spacing=12
    ├── Button "Cancel"                    [btn-ghost]
    └── Button "Start Game"               [btn-primary]
```

The `GridPane` with aligned labels and fields is the main change: it replaces the current
alternating label-then-field `VBox` stacking, which causes field widths to vary and labels
to float loose. The `Separator` between the player fields and the rules section adds visual
grouping without a card-within-card (which would over-nest). The `section-heading` label
("Rules") applies the small-caps subdued color from the theme.

**Online setup (`online-setup.fxml`) redesign:**

The online setup has two modes (Create / Join) toggled by `ToggleButton`s. The redesign makes
the mode selector visually prominent and groups connection params separately from game params.

```
overlay-card (VBox, spacing=20, minWidth=440)
├── Label "Online Game"                    [dialog-title]
├── HBox spacing=0 (segmented toggle, full width)
│   ├── ToggleButton "Create Game"         [toggle-button] width=50%
│   └── ToggleButton "Join Game"           [toggle-button] width=50%

│   ├── Label "Connection"                 [section-heading]

│   └── (join mode only) Label "Join Code" + TextField fx:id="joinCodeField"
├── Separator
├── Label "Rules"                          [section-heading] (hidden in join mode)
├── ComboBox fx:id="rulesetBox" maxWidth=Infinity (hidden in join mode; joiner uses server's ruleset)
├── Label fx:id="errorLabel"               [red, managed=false, visible=false]

    ├── Button "Cancel"                    [btn-ghost]
    └── Button "Connect"                   [btn-primary]
```

Key changes vs. current:
- Toggle buttons are side by side taking the full card width (each 50%). The `card` inner box
  for connection params visually groups them. The `section-heading` treatment matches offline.
- The `ComboBox` for ruleset is hidden in join mode — the joiner receives the ruleset from
  the server (encoded in the `SUCCESS` message), so showing a ruleset picker would be
  misleading. The controller must hide/show it on toggle.
- The join code field stays visible only in join mode (already handled by the controller
  with `managed`/`visible` binding — no change needed there).

**No new CSS files are added.** The segmented-toggle appearance for the two `ToggleButton`s is
achieved by setting `minWidth` to equal portions of the card width via `HBox.hgrow=ALWAYS` on
each button — JavaFX 21 stretches them to fill the row. The selected/unselected states are
already styled in all theme CSS files under `.toggle-button` and `.toggle-button:selected`.

## Components

### `AbstractChessRuleset`
Package: `io.github.conava.chess.core.logic.ruleset`

Extracted directly from `StandardChessRuleset`. Contains all methods except `getStartBoard`.
Marked `abstract`. `getSudoLegalSquares` is promoted from `private` to `protected`.

Template method: `getSudoLegalSquares` dispatches piece type. The King case delegates to
`getPseudoLegalKingSquares(Square, Board, List<Move>)` — a new `protected` method that
`AbstractChessRuleset` implements using `PossibleStandardKingMoves` and that `Chess960Ruleset`
overrides using `PossibleChess960KingMoves`.

### `StandardChessRuleset`
Package: `io.github.conava.chess.core.logic.ruleset.standardChessRuleset`

Extends `AbstractChessRuleset`. Implements only `getStartBoard` — delegates to
`PossibleStandardPosition` as today.

### `Chess960Ruleset`
Package: `io.github.conava.chess.core.logic.ruleset.chess960Ruleset`

Extends `AbstractChessRuleset`. Implements:
- `getStartBoard` — delegates to `Chess960StartPosition`, stores the result.
- `getPseudoLegalKingSquares` — returns a `PossibleChess960KingMoves` instance.
- `getLegalSquares` — overrides to replace `Math.abs(delta)==2` castling detection with
  rook-file detection and walks all transit squares between king start and king dest.
- `getIndex()` — returns the Scharnagl index (int 0–959).

Two constructors:
- `Chess960Ruleset()` — generates random position, computes index.
- `Chess960Ruleset(int scharnaglIndex)` — reconstructs position from index.

### `Chess960StartPosition`
Package: `io.github.conava.chess.core.logic.ruleset.chess960Ruleset`

Two static factory methods:
- `generate(Player, Player)` — five-step constrained random, returns `Square[][]`.
- `fromIndex(int index, Player, Player)` — Scharnagl reconstruction, returns `Square[][]`.

Also exposes a `computeIndex(Pieces[] backRank)` utility for converting a generated back rank
to its Scharnagl index.

### `PossibleChess960KingMoves`
Package: `io.github.conava.chess.core.logic.ruleset.possibleMoves`

Mirrors `PossibleStandardKingMoves`. `canCastleToward` walk logic is identical. The
difference: instead of adding `board.getSquare(rank, 2)` or `board.getSquare(rank, 6)`, it
adds the square where the eligible rook was found (the rook's current file).

### `CastleMove` (modified)
Adds two `int` fields:
- `rookOriginFile` (default -1)
- `kingDestFile` (default -1)

Adds constructor: `CastleMove(Square start, Square end, int rookOriginFile, int kingDestFile)`.

The existing single-arg-pair constructor is unchanged — all existing usages continue to work.

### `Board.handleCastleMove` (modified)
```
if (move.rookOriginFile >= 0):   // Chess960 path
    rookOldSquare = getSquare(rank, rookOriginFile)
    if (kingDestFile < kingStartFile):   // queenside
        rookNewSquare = getSquare(rank, 3)
        actualKingDest = getSquare(rank, 2)
    else:                                // kingside
        rookNewSquare = getSquare(rank, 5)
        actualKingDest = getSquare(rank, 6)
    // relocate king from endSquare (rook's file) to actualKingDest
else:
    existing hardcoded logic (unchanged)
```

### `Game.movePiece` (modified)
```java
boolean isStandardCastle = piece instanceof King
    && Math.abs(end.getX() - start.getX()) == 2;
boolean isChess960Castle = piece instanceof King
    && end.getPiece() instanceof Rook
    && end.getPiece().getPlayer().equals(piece.getPlayer())
    && !((Rook) end.getPiece()).hasMoved();
if (isStandardCastle || isChess960Castle) {
    boolean kingside = end.getX() > start.getX();
    move = new CastleMove(start, end,
        /*rookOriginFile=*/ end.getX(),
        /*kingDestFile=*/   kingside ? 6 : 2);
}
```

`isChess960Castle` will never fire in a standard game (rooks start on a1/h1/a8/h8, not
squares the king legally travels to), so this guard is safe in both modes.

### `Game.createRuleset` (modified)
```java
case CHESS960 -> new Chess960Ruleset();
// or when a position index is available:
case CHESS960 -> new Chess960Ruleset(scharnaglIndex);
```

`createServerGame` gains an overload that accepts the position index when Chess960 is selected.

### `Game.computePositionKey` / `Game.castlingChar` (modified)
Currently hard-code king x=4, rook x=0 and x=7. Changed to scan dynamically:
- `findKingFile(int rank)` — scans rank for a `King` belonging to the player.
- `findRookFiles(int rank, Player)` — scans rank for unmoved `Rook` pieces.

These are `private` methods; the change has no external API impact.

### `GameInstance` (server, modified)
When `ruleset == CHESS960`:
- On `CREATE_GAME`: generate a `Chess960Ruleset`, store its `getIndex()` as `positionIndex`.
- `JOIN_CODE` message content extended: `joinCode=<id> position=<index> ruleset=CHESS960`.
- `SUCCESS` message for black player extended: `player=black position=<index> ruleset=CHESS960`.
- `startGame()` passes the index to `Game.createServerGame()` via the new overload.

When `ruleset == STANDARD`:
- No change — `position` key is absent; clients treat absent key as standard.

### `RulesetOptions` (modified)
```java
public enum RulesetOptions {
    STANDARD("Standard Chess"),
    CHESS960("Chess 960");

    private final String displayName;
    RulesetOptions(String displayName) { this.displayName = displayName; }

    @Override public String toString() { return displayName; }
}
```

### `OfflineSetupController` (modified)
Controller logic is unchanged. The FXML layout change requires no code changes — the
controller binds to the same `fx:id` references. The only code consideration: if the
`GridPane` layout changes column-constraint sizing, the controller need not be touched.

### `OnlineSetupController` (modified)
Two code changes beyond the FXML layout:
1. Hide `rulesetBox` (and its label) in join mode — set `managed=false, visible=false`.
   Already the controller toggles `joinCodeField` this way; apply the same pattern.
2. In the `SUCCESS` message handler (where `player=black` is received), read
   `position` and `ruleset` parameters to determine whether to construct
   `Chess960Ruleset(index)` before starting the game.

## Data Flow

### Starting an offline Chess960 game
1. User opens offline setup, selects `Chess 960` in the `ComboBox`.
2. `OfflineSetupController.getRuleset()` returns `RulesetOptions.CHESS960`.
3. `Chess.startGame(false, CHESS960, ...)` → `Game.createGame(false, CHESS960, ...)` →
   `createRuleset(CHESS960)` → `new Chess960Ruleset()`.
4. `Chess960Ruleset` constructor calls `Chess960StartPosition.generate(p0, p1)`.
5. `Game` calls `ruleset.getStartBoard(p0, p1)` — receives the randomized board.
6. Game proceeds identically to standard chess.

### Starting an online Chess960 game (creator)
1. Creator selects `Chess 960`, clicks Connect.
2. Client sends `CREATE_GAME ruleset=CHESS960 playerName=<name>`.
3. Server (`GameInstance`) generates position, stores `positionIndex`, sends:
   `JOIN_CODE joinCode=<id> position=<positionIndex> ruleset=CHESS960`.
4. Client reads `position` and `ruleset` from `JOIN_CODE`, constructs
   `Chess960Ruleset(positionIndex)`.
5. `WaitingController` shows the join code.

### Starting an online Chess960 game (joiner)
1. Joiner enters join code, clicks Connect.
2. Client sends `JOIN_GAME gameId=<id> playerName=<name>`.
3. Server sends `SUCCESS player=black position=<positionIndex> ruleset=CHESS960`.
4. Client reads `position` and `ruleset`, constructs `Chess960Ruleset(positionIndex)`.
5. Both clients are now synchronized on the same position.

### Chess960 castling — move execution
1. `GameController` receives click on king's square, then click on rook's square.
2. `chess.getLegalSquares(kingSquare)` returns the rook's square (from `PossibleChess960KingMoves`).
3. `chess.movePiece(kingSquare, rookSquare)` is called.
4. `Game.movePiece` detects `isChess960Castle`, creates
   `CastleMove(start, rookSquare, rookOriginFile, kingDestFile)`.
5. `isMoveValid` confirms the rook's square is in the legal list.
6. `board.executeMove` → `handleCastleMove` uses explicit fields to place king on c/g file,
   rook on d/f file.

## Data Model

No schema changes. New in-memory state:
- `Chess960Ruleset` holds `Pieces[]` back-rank and `int scharnaglIndex`.
- `GameInstance` (server) holds `int positionIndex` when `Chess960` is active.
- `CastleMove` gains two `int` fields (`-1` sentinels for standard chess).

No serialization is required by this feature.

## API Design

### Wire protocol extensions (backward compatible)

| Message | Direction | New keys | Present when |
|---------|-----------|----------|-------------|
| `CREATE_GAME` | client→server | _(none — server generates position)_ | — |
| `JOIN_CODE` | server→client | `position=<int>` `ruleset=CHESS960` | Chess960 games only |
| `SUCCESS` (player=black) | server→client | `position=<int>` `ruleset=CHESS960` | Chess960 games only |

All new keys are additive. Clients that do not understand them (e.g. old `STANDARD` clients)
receive none of them.

### `Chess960Ruleset` public surface
```java
Chess960Ruleset()                     // random position
Chess960Ruleset(int scharnaglIndex)   // deterministic from index
int getIndex()                        // Scharnagl index 0–959
Pieces[] getBackRank()                // white's back rank for display
```

### `Chess960StartPosition` public surface
```java
static Square[][] generate(Player p1, Player p2)
static Square[][] fromIndex(int index, Player p1, Player p2)
static int computeIndex(Pieces[] backRank)
```

## Error Handling

- `Chess960StartPosition.generate` uses `java.util.Random`. The constrained algorithm cannot
  produce duplicates or invalid arrangements by construction. No validation pass needed.
- `Chess960StartPosition.fromIndex` validates `index` is in `[0, 959]`; throws
  `IllegalArgumentException` for out-of-range values.
- If no unmoved rook is found during `PossibleChess960KingMoves.canCastleToward`, it returns
  false — no new error path needed.
- `CastleMove` with `rookOriginFile = -1` follows the existing path in `handleCastleMove`.
  Existing code cannot accidentally trigger the Chess960 path.
- If the `position` key is absent from a `JOIN_CODE` or `SUCCESS` message (e.g. old server),
  `OnlineSetupController` falls back to `new Chess960Ruleset()` and logs a warning.

---

## Security Considerations

The `position` parameter is an integer 0–959. The client validates range before constructing
`Chess960Ruleset(index)` — out-of-range values produce an `IllegalArgumentException` that the
application catches and treats as a server error (same path as a malformed `gameState` value).

## Testing Strategy

New test classes (all in `modules/core/src/test`):

- `Chess960StartPositionTest`: verify bishop color constraint (one dark, one light), verify
  king-between-rooks invariant, verify all 8 back-rank squares filled, run 1000 iterations.
  Verify `fromIndex(computeIndex(rank), ...)` round-trips correctly for a sample of positions.
- `Chess960CastlingTest`: construct known positions with king not on e-file, verify legal
  moves include the rook's square, verify board state after castling places king and rook on
  correct files (g/f kingside, c/d queenside).

## Migration Plan

- `StandardChessRuleset` is refactored (methods move to `AbstractChessRuleset`) but its
  public interface is unchanged. No callers outside `core` reference it directly.
- `CastleMove` gains fields defaulting to `-1`. All existing `new CastleMove(start, end)`
  call sites are unaffected.
- `Board.handleCastleMove` gains a branch only reachable by the new constructor.
- `RulesetOptions.toString()` changes from `"STANDARD"` to `"Standard Chess"`. The only known
  usages of `toString()` for `STANDARD` are the `ComboBox` display (which the change improves)
  and any logging statements (cosmetic only). Server parsing uses `valueOf()`, not `toString()`.
- Wire protocol messages gain optional keys. Old clients never send or receive Chess960
  messages, so existing connections are unaffected.
