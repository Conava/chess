### Summary

The Chess960 feature is well-architected. The AbstractChessRuleset extraction is clean, the
template-method hooks (`getPseudoLegalKingSquares`, `isCastlingCandidate`, `buildCastleMove`)
are well-placed, and the deferred-init pattern for online games is generic enough to support
future rulesets. The design document (Decision 1-9) was followed faithfully. The most
significant issues are a DRY violation between the two king-move generators, an unused
variable, and a performance concern in the Chess960 transit-square check. No critical bugs
were found.

### Findings

#### DRY (Don't Repeat Yourself)

1. **File:** `modules/core/src/main/java/.../possibleMoves/PossibleChess960KingMoves.java` (full class)
   **File:** `modules/core/src/main/java/.../possibleMoves/PossibleStandardKingMoves.java` (full class)
   **Category:** DRY / Simplification
   **Severity:** Important
   **Confidence:** 0.95
   **What's wrong:** `PossibleChess960KingMoves` (249 lines) duplicates most of
   `PossibleStandardKingMoves` (145 lines). The one-step adjacency move generation is
   identical (same `arrY`/`arrX` offsets, same bounds check, same occupancy filter). The
   `canCastleKingside`/`canCastleQueenside` guard methods are identical. The `canCastleToward`
   walk logic is structurally identical — the only difference is that the standard class
   returns `true` when it finds the rook, while the Chess960 class additionally calls
   `isCorridorClear`. The `isInBounds` helper is copy-pasted verbatim. The `findRookSquare`
   method repeats the same walk a third time (once for `canCastleToward`, once for
   `findRookSquare`).
   **Suggested improvement:** Extract a shared abstract base class
   `AbstractKingMoveGenerator` containing the one-step moves, `isInBounds`,
   `canCastleKingside`/`canCastleQueenside`, and the `canCastleToward` walk. The walk can
   call an abstract `onRookFound(int rank, int kingFile, int rookFile, boolean kingside)`
   hook — Standard returns `true`, Chess960 returns `isCorridorClear(...)`. The castling
   target-square selection (fixed file vs. rook file) can be another hook. This eliminates
   approximately 80 lines of duplicated code. Alternatively, merge `canCastleToward` and
   `findRookSquare` in `PossibleChess960KingMoves` into a single walk that returns both the
   eligibility boolean and the rook square, eliminating the redundant second walk.

2. **File:** `modules/core/src/main/java/.../chess960Ruleset/Chess960Ruleset.java:327-343` (`isKingTransitAttacked`)
   **File:** `modules/core/src/main/java/.../ruleset/AbstractChessRuleset.java:104-135` (`getLegalSquares` castling block)
   **Category:** DRY
   **Severity:** Important
   **Confidence:** 0.82
   **What's wrong:** Both the standard and Chess960 `getLegalSquares` implementations perform
   the same pattern: deep-copy board, simulate move, check for check. The Chess960 override
   repeats the entire non-castling branch verbatim (lines 249-258) — it is a copy of lines
   122-131 in `AbstractChessRuleset`. The only difference is the castling branch.
   **Suggested improvement:** Restructure `AbstractChessRuleset.getLegalSquares` so the
   non-castling deep-copy-and-check logic is in a private helper method (e.g.
   `isLegalAfterSimulation`). The Chess960 override then only needs to provide its own
   castling branch, calling the shared helper for non-castling moves.

#### Performance

6. **File:** `modules/core/src/main/java/.../chess960Ruleset/Chess960Ruleset.java:327-343` (`isKingTransitAttacked`)
   **Category:** Performance
   **Severity:** Important
   **Confidence:** 0.85
   **What's wrong:** For each transit square between the king and its castling destination,
   the method creates a full deep copy of the board (`board.getCopy()`) and runs a complete
   `isCheck` scan. In Chess960, the king can be up to 5 squares away from its destination
   (e.g., king on file 1 castling kingside to file 6). Combined with the final-position
   simulation copy, this means up to 6 deep copies per castling candidate per legal-move
   generation call. Since `hasAnyLegalMove` iterates all pieces, this can produce dozens of
   deep copies per turn in positions where the king has castling pseudo-legal.
   **Suggested improvement:** This is an existing performance debt (noted in CLAUDE.md as
   "Known performance debt: hasAnyLegalMove is O(moves x pieces)"). For Chess960 it is
   amplified. A targeted fix: skip transit-square checks in `hasAnyLegalMove` since it only
   needs to find one legal move (not enumerate all). Or: check transit squares by computing
   attacked-squares without full board copies — use the reverse-attack scan from `isCheck`
   directly on the transit square, avoiding the copy entirely.

### Positive Observations

1. **Template method hierarchy is well-designed.** The `AbstractChessRuleset` extraction
   provides exactly the right extension points (`getPseudoLegalKingSquares`,
   `isCastlingCandidate`, `buildCastleMove`). The `StandardChessRuleset` shrinks to a
   one-method class (28 lines), which is a clean outcome from the extraction.

2. **Deferred board initialization is generic and forward-looking.** The
   `Game(RulesetOptions, String, String, boolean deferBoardInit)` constructor with the
   `initializeBoard(Ruleset)` double-call guard is a clean pattern that works for any
   future ruleset requiring server-provided parameters. The null guards in `OnlineGame`
   (`getLegalSquares`, `isLocalPlayerPiece`, `backupGameState`) are thorough.

3. **`Ruleset.deserializeMove` keeps ruleset knowledge inside the ruleset.** The default
   method on the interface with the Chess960 override is a textbook application of the
   Strategy pattern. `OnlineGame` and `GameInstance` both call the same
   `ruleset.deserializeMove(...)` with no `instanceof` checks or switch statements.

4. **`Chess960StartPosition.computeIndex` is the proper inverse of `fromIndex`.** The
   round-trip property (`computeIndex(fromIndex(i)) == i`) is documented and testable.
   The N5 encoding table is clear and compact.

5. **`Board.handleCastleMove960` clear-then-place ordering.** The explicit four-step
   sequence (clear king, clear rook, place king, place rook) correctly handles all
   Chess960 overlap scenarios (king's dest = rook's origin, etc.).

6. **Castling-rights position key (`appendCastlingRights`) is generic.** The dynamic scan
   for king and rooks on the back rank works correctly for both standard and Chess960
   positions, avoiding any hardcoded file assumptions in threefold repetition detection.

### Refactoring Suggestions

**Unified King Move Generator (findings #1):**
Three findings point to the same structural issue: `PossibleChess960KingMoves` is largely a
copy of `PossibleStandardKingMoves` with two behavioral differences (corridor check and target
square selection). A single refactoring — extracting an abstract base with two small hooks —
would eliminate approximately 80 lines of duplication and make future king-move changes
(e.g., a new variant) a one-place edit. This is the highest-value refactoring opportunity on
the branch.

**Shared Legal-Move Filter (findings #2, #7):**
The non-castling branch of `getLegalSquares` is duplicated between `AbstractChessRuleset` and
`Chess960Ruleset`. Extracting the deep-copy-simulate-check pattern into a shared helper would
reduce `Chess960Ruleset.getLegalSquares` to only its castling-specific logic, eliminating the
divergence risk and about 10 lines of duplication.

Both refactorings are safe to perform after this review cycle and do not change any observable
behavior.

#### Gap 3 -- `deserializeMove` silent fallback produces wrong CastleMoves (Severity 7, Confidence 0.88)
